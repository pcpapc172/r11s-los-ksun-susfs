## r11s LineageOS — KernelSU-Next + SUSFS v2.0.0

Rebuilt on ExtremeXT's updated boot.img source, and fixes the recurring
KernelSU-Next Manager version-compatibility problem for good.

### Corrected kernel source

The previous build (and this repo's `kernel_source/`) was based on
ExtremeXT's public `lineage-23.2` branch, which turned out to be stale —
their actual shipped boot.img is built from a private tree. Tracing the
new boot.img's embedded version banner (`5.10.260-gd0703f36a4e0`) led to
the real commit: **LineageOS's own official
`android_kernel_samsung_s5e9925` repo**, `lineage-23.2`/`lineage-24.0`
branches, commit `d0703f36a4e0`.

That commit brings real upstream fixes across:
- Battery/fuel gauge (`sec_battery.c`, `max77705_fuelgauge.c`)
- Camera ISP (`is-hw-*.c`, `is-core.c`, `is-device-*.c`, and more)
- DRM (`exynos_drm_hdr`, `exynos_drm_plane`, `exynos_drm_dqe`)
- `drivers/android/binder.c` / `binder_alloc.c`
- Input (`drivers/input/input.c`, `stm_core.c`)
- Device tree (`r11s_*.dts` panel revisions)

`kernel_source/` in this repo is built from that corrected source
instead of ExtremeXT's stale fork. Kconfig baseline is unchanged
(confirmed byte-identical `.config` between the old and new boot.img
via `extract-ikconfig`).

### The KSU_VERSION saga, and the actual fix

Getting KernelSU-Next's embedded version to agree with the installed
Manager app took several iterations:

1. Pinned `pershoot/KernelSU-Next` (`dev-susfs`) to a specific commit,
   copied in as a plain file tree (no `.git`). Worked initially
   (`KSU_VERSION=30200`, matching Manager `v3.3.0`).
2. Upstream `dev-susfs` got rebased and that commit became unreachable.
   Re-cloning picked up a new HEAD; a naive recompute gave `33274` —
   *higher* than the installed Manager, so Manager refused to work
   ("needs 33274 or higher").
3. Reverted to the hardcoded `30200` to fix that — but by then the
   installed Manager had moved on too, and `30200` was now *lower* than
   what it expected. Opposite failure.

Root cause: `KSU_VERSION` is just `30000 + (commit count on upstream's
dev branch)` — it only ever increases as upstream commits land. The
kernel driver gets whatever that count is when the kernel is built; the
Manager APK gets whatever that count is when *it* was built, as a
completely separate, independently-timed release. They only agree when
both are built from the same commit at the same time. Hardcoding either
side is chasing a number that never stops moving.

**The fix**: stop hardcoding it entirely.
- CI now clones `pershoot/KernelSU-Next` (`dev-susfs`) fresh, with full
  history, before every build, instead of building from a stale copy
  baked into the repo. The hand-maintained `KSU_VERSION_FALLBACK` /
  `KSU_VERSION_TAG_FALLBACK` overrides are removed from `kernel/Kbuild`
  so its own git-based version formula (merge-base commit count against
  the `dev` branch) runs for real — the same mechanism official release
  builds use.
- For the Manager app side: pershoot's fork has no dedicated GitHub
  Release for `dev-susfs` to pin to. But the Manager app computes its
  own `versionCode` with the *identical* formula (merge-base commit
  count against `origin/dev`), so a Manager built from the same
  upstream commit as the kernel will always compute the same number.
  Upstream `KernelSU-Next/KernelSU-Next`'s own CI (`Build Manager CI`,
  on the `dev` branch) builds exactly that — official-signed, no custom
  allowlist changes needed. This release bundles the `manager` and
  `manager-spoofed` APKs from that CI (built at commit `88feb688`, the
  same commit our kernel build's merge-base resolved to), both
  reporting `KSU_VERSION=33264` / UAPI v4, matching this kernel.
- `manager_apk/KernelSU-Next-Manager.apk` and
  `manager_apk/KernelSU-Next-Manager-spoofed.apk` in this repo are
  those two builds — install whichever one you prefer (only the signing
  cert is checked; package name isn't restricted).

### Validation

`vendor_boot` ramdisk:

  table: **0**

  same as every previous build)

The `TRIM_UNUSED_KSYMS` fix holds on the corrected source, and the
kernel + Manager pairing in this release has been confirmed working on
a real device.
